Architecture and invariants

VeriLens is two programs with one JSON contract between them: a C++ structural extractor (core/) and a TypeScript/React/SVG viewer (packages/web/). This page describes the pipeline and the rules the viewer never breaks.

The core is a structural extractor

It is not a compiler. The parser keeps what a schematic needs: module declarations with ports, directions and widths; instantiations with their port connections; net declarations; assign statements with full expression trees; and always blocks with sensitivity lists and statement trees. Everything else is skipped.

Instantiations and net declarations share the IDENTIFIER IDENTIFIER shape, so the parser runs a light first pass to collect module names, and uses look-ahead (#( or IDENTIFIER () for modules defined in other files. The linker then resolves every instance against the whole project. Unresolved instances are kept in the output with resolved: false so the viewer can draw them as black boxes.

The contract

gen_ast emits an array of modules; the shape is defined by moduleToJson in core/Parser.cpp, and golden files in core/tests/parser/*.ast.json pin it down. The viewer reads it through a single adapter. Instance connections carry a parsed expr tree, so the viewer never re-parses Verilog text and contains no regular-expression parsing. A // verilens: top comment marks the top module. The field reference lives on the Input formats page.

Viewer invariants

These are the rules the viewer is built around. Tests in packages/web/tests/ and packages/web/e2e/ guard them.

  1. Data, rules, geometry and UI state are separate. Design is what exists. LayoutFile is how to arrange it. ModuleLayout is computed geometry. UI state lives in the store. Layout rules never change connectivity, layout code never mutates the design, and no fake circuit edges are added to the design to express layout wishes.
  2. Geometry changes only on design load, applying a layout file, or an explicit Re-layout. Selection, highlighting, camera and module expansion never trigger layout.
  3. Expansion moves nothing. Every expandable instance owns a fixed frame from the parent's layout. Expanded contents render in a clipped nested <svg> under the header, in the child's own coordinates, scaled to fit. Siblings, the frame, port anchors, external routes and the camera stay identical. Layouts are cached per instance path, so collapse and re-expand give the same picture. Large interiors are read with Focus module, not by growing frames.
  4. Nothing is draggable. Components, ports and wires have no drag or edit handlers. Panning starts only on the background.
  5. Wires are routed after all node movement. The engine runs validate → layered candidate → constraint solve → route → verify. A node is never moved after routing. Junction dots mean a branch; crossings get no dot.
  6. Layout jobs are versioned. A result is applied only if it is still the newest for its scope key, so a slow layout can never overwrite a newer one.
  7. Deterministic. Same design plus same rules gives an identical layout. No randomness, stable iteration order.
  8. Honest rendering. Undriven or multiply-driven nets, unconnected ports, black boxes, constants and implicit nets are shown or reported, never repaired or hidden.

Layout engine in one paragraph

layered.ts assigns components to left-to-right layers from the connectivity (breaking feedback cycles on the thinner bundle) and orders them to reduce crossings. constraints.ts then applies the rules from the layout file: required rules must hold or the layout is rejected with a diagnostic; preferred rules are satisfied when they do not conflict. router.ts draws orthogonal wires over the final positions. engine.ts verifies the result against the invariants before the store accepts it. See the Layout DSL for the rule vocabulary.

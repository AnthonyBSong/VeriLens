Contributing

VeriLens is MIT licensed and developed on GitHub at AnthonyBSong/VeriLens. Bug reports with a small .sv file that reproduces the problem are the most useful thing you can send.

Set up

Follow Installation, then make sure both test suites pass before you change anything:

cmake -S . -B build && cmake --build build
cd build && ctest
cd ../packages/web && npm install && npm test && npm run test:e2e

Working on the core

  • Parser tests live in core/tests/parser and compare against JSON goldens (*.ast.json). When you change the JSON shape on purpose, regenerate them with python3 core/tests/parser/gen_golden.py and review the diff.
  • Add a lexer, parser or validator test for every new construct. A failing input file is a good first commit for a bug report.
  • The core stays a structural extractor. Features that do not change what a schematic shows (expression evaluation, elaboration, simulation) are out of scope.

Working on the viewer

  • npm run dev serves the bundled demo at http://localhost:5173; add ?sample=conflict or ?focus=top/compute to jump to a state.
  • Changes to layered.ts, constraints.ts, router.ts or store.ts need a test in packages/web/tests/ (vitest) or packages/web/e2e/ (Playwright, uses the installed Google Chrome).
  • Never re-parse Verilog text in the viewer. Everything you need is in the adapter's Design; if it is missing, extend the core and the contract instead.
  • Keep the eight invariants. In particular: no drag handlers, no layout triggered by selection or expansion, no node moved after routing, and no net or port hidden to make a picture cleaner.
  • If you touch samples/demo/demo.sv, rebuild the samples with npm run gen:samples.

Layout rules for real designs

A good contribution that needs no code is a layout.yaml for a public design, together with the command line that renders it. The ProcBase.layout.yaml in core/tests/examples is the reference; see Examples.

Pull requests

  • One topic per PR. Describe what the schematic looked like before and after when the change is visual; a screenshot from Export HTML is ideal.
  • Run both test suites. CI does not yet gate merges, so the author is the gate.
  • Keep the docs in step: README.md, packages/web/README.md, packages/web/docs/FORMATS.md, and this site (the gh-pages branch is plain HTML; edit the page and push).

This site

The documentation is hand-written HTML on the gh-pages branch with no build step. assets/site.js adds the shell (navigation, table of contents, pager) around each page's <main>. The live demo under demo/ is the viewer's single-file build with a sample design embedded; regenerate it with npm run build and copy dist/index.html. The screenshots come from packages/web/scripts/dev/shot-docs.mjs run against npm run preview.
